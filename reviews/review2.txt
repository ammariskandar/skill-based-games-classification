ID: REVIEW-2-03
Severity: Medium
Area: Frontend API transport
Type: Illusion of timeout, cancellation, and cleanup
Status relative to Review 1: New in Review 2
Finding: The SBGC-34 timeout and caller-cancellation lifecycle ends when response headers arrive, not when the response operation and body handling finish; ignored response bodies are also neither consumed nor cancelled.
Evidence: apps/frontend/src/lib/server/api/client.ts:88-110 starts the timer and caller abort listener. fetch resolves at client.ts:119-124. cleanup() is called immediately at line 147. Body handling occurs afterward at lines 149-192, including await response.text() at line 173. Non-2xx responses return at lines 149-155 and non-JSON responses return at lines 162-169 without consuming or cancelling response.body. docs/frontend-api-layer.md:64-69 describes an eight-second request timeout and clean timeout/caller-abort distinction without qualifying that protection as headers-only. Fetch resolves after status and headers, before body completion; aborting can affect later body reads, as defined by the [Fetch Standard](https://fetch.spec.whatwg.org/) and described in [MDN’s Fetch guidance](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch). Node’s Undici guidance recommends consuming or cancelling every response body because garbage collection is not a deterministic connection-release mechanism: [Undici garbage-collection guidance](https://github.com/nodejs/undici#garbage-collection).
Why it matters: An upstream can send headers and then stall, leaving an Astro SSR invocation pending beyond timeoutMs. Caller cancellation after header receipt is ignored. Body-read failures can be reported as parse failures. Repeated Django or gateway error responses can hold network resources during the very failure periods in which connection reuse matters most.
Current impact: No Astro route imports this client, so no user-facing request currently reaches the affected branches.
Future impact: The first dynamic route could exceed Vercel execution limits, continue upstream work after the inbound request is cancelled, misclassify failures, or amplify an upstream degradation through poor connection reuse.
Recommended action: Treat fetch plus body consumption or explicit body cancellation as one operation. Retain timeout and caller cancellation until every result path has consumed or cancelled the body, and place cleanup in a final operation-lifetime path. Preserve the source of cancellation. Test slow headers, slow bodies, pre-abort, abort during body consumption, timeout during body consumption, body-stream failure, and cleanup on every return branch.
Suggested Jira scope: SBGC-34 corrective follow-up, reconciled with SBGC-90 and SBGC-92 before the first endpoint integration.
Confidence: High

ID: REVIEW-2-04
Severity: Medium
Area: Frontend API URL and redirect boundary
Type: Security and transport-boundary precursor
Status relative to Review 1: New in Review 2
Finding: Relative-path enforcement constrains only the initial caller string; base-URL validation, query composition, path-prefix containment, and redirect behaviour remain incomplete.
Evidence: client.ts:28-37 checks only whether DJANGO_API_URL is truthy and removes trailing slashes. It does not validate scheme, credentials, host, query, fragment, whitespace, or production HTTPS. resolveUrl at lines 43-61 concatenates strings. Dot-segment normalization can escape a configured base-path prefix. The scheme-regex branch at lines 54-60 is unreachable because line 47 first rejects every string not beginning with "/". getJSON at lines 197-207 always appends "?"; a path already containing a query or fragment is composed incorrectly. fetch at lines 119-124 does not set redirect, so the Fetch default is follow. No check of response.redirected, response.url, final origin, or final method exists. Django CommonMiddleware is active at apps/backend/config/settings.py:63, and Django’s default APPEND_SLASH behaviour can redirect unmatched paths; Django warns that redirecting requests can lose POST data in its [APPEND_SLASH documentation](https://docs.djangoproject.com/en/6.0/ref/settings/#append-slash). The [Fetch redirect algorithm](https://fetch.spec.whatwg.org/#http-redirect-fetch) permits 301/302 POST and 303 non-GET redirects to change the method to GET.
Why it matters: A typo in an API trailing slash may be silently masked. A future POST can receive a successful final GET response even though the mutation did not occur. A trusted Django or proxy endpoint that redirects to another origin can cause the Astro server to leave its intended backend origin. That is a latent open-redirect/SSRF composition risk, not an active arbitrary-host SSRF in the present application.
Current impact: No route invokes getJSON or postJSON. The initial caller checks do reject absolute and protocol-relative path arguments, so no current arbitrary absolute URL input was found.
Future impact: Incorrect search queries, requests outside an intended API path prefix, misleading configuration errors, false mutation success, and erosion of the server-to-server origin boundary.
Recommended action: Parse and validate DJANGO_API_URL as an explicit HTTP(S) URL contract; disallow credentials, query, and fragment; define production HTTPS requirements; construct request URLs using URL semantics; merge or prohibit pre-existing path queries; assert final origin and any base-path prefix; and adopt an explicit redirect rejection policy unless a specific endpoint contract requires otherwise. Test all slash, query, fragment, dot-segment, and 301/302/303/307/308 cases.
Suggested Jira scope: One URL/redirect hardening scope under the SBGC-34/SBGC-90 transport work, with environment validation coordinated through SBGC-91.
Confidence: High

ID: REVIEW-2-05
Severity: Medium
Area: Frontend API result and error contract
Type: Illusion of normalized error handling
Status relative to Review 1: New in Review 2
Finding: Known runtime states and materially different failure classes are hidden behind unsafe casts, contradictory status fields, or misleading error categories.
Evidence: apps/frontend/src/lib/server/api/types.ts:5-9 requires data: T for every ApiSuccess<T>, but client.ts:157-160 returns undefined as unknown as T for every 204. JSON.stringify(body) occurs inside the broad fetch try at client.ts:119-124, so cyclic values and BigInt serialization failures become NETWORK_ERROR at lines 139-144. Invalid configured URLs can also become NETWORK_ERROR rather than CONFIG_ERROR. response.text() and JSON.parse() share one catch at lines 171-189, causing stream failures and syntax failures to receive the same parse-oriented message. ApiFailure.status exists at types.ts:12-16, while ApiError.status exists separately at lines 32-40; the client populates only the outer status. docs/frontend-api-layer.md:52-56 says ApiError.status is present when available. UNKNOWN_ERROR is declared and documented but never emitted. Raw caught Error objects are stored in cause at client.ts:141-143 and 186-188 even though types.ts:35-40 and docs/frontend-api-layer.md:54-56 promise safe diagnostic context without stack traces. Header merging at client.ts:112-115 is case-sensitive before Fetch normalisation, allowing duplicate content-type or accept names with different casing. Response media-type matching at lines 162-163 is case-sensitive substring matching.
Why it matters: The discriminated union appears stronger than the runtime contract. A caller can narrow ok === true and dereference data after a 204 even though no data exists. Operators and callers cannot reliably distinguish caller serialization, configuration, network, response-stream, and JSON-syntax failures. Duplicate status locations have already diverged. Future retry, alerting, and UI decisions can therefore be based on the wrong category.
Current impact: There is no route consumer. Direct use would already exhibit these semantics.
Future impact: Runtime exceptions on bodyless endpoints, false success, caller-specific workarounds, misleading observability, and accidental exposure of internal diagnostic objects.
Recommended action: Model no-content success explicitly; never cast known undefined to arbitrary T. Select one authoritative status location. Serialize before entering the network catch. Separate request construction, network, body-read, and parse failures where actionable. Remove unreachable categories or add a genuine final normalization boundary. Treat cause as sensitive internal diagnostics rather than display-safe data. Use Headers for case-normalized header policy and parse media types deliberately. Retain the documented statement that TypeScript generics are not runtime schema validation.
Suggested Jira scope: Error/result-contract consolidation under an SBGC-34 corrective follow-up and SBGC-92; coordinate future structured backend errors with SBGC-89 and SBGC-100.

Error-handling and failure-mode assessment

Observed SBGC-34 result behaviour:

- Missing DJANGO_API_URL:
  CONFIG_ERROR.

- Empty path:
  CONFIG_ERROR.

- Path without leading slash:
  CONFIG_ERROR; the message reflects the rejected path.

- Protocol-relative path:
  CONFIG_ERROR.

- Absolute URL:
  Rejected by the leading-slash rule; the dedicated scheme test is unreachable.

- Malformed or unsupported base URL:
  Generally reaches Fetch and becomes NETWORK_ERROR rather than CONFIG_ERROR.

- Existing query plus getJSON params:
  A second "?" is appended and composition is incorrect.

- Fragment plus getJSON params:
  Appended parameters can become part of the fragment and never reach Django.

- Redirect:
  Followed transparently. Final origin and method are not validated.

- Caller signal already aborted:
  ABORTED.

- Caller abort before headers:
  Normally ABORTED.

- Timeout before headers:
  Normally TIMEOUT.

- Caller abort or timeout after headers:
  No longer active because cleanup already removed the listener and timer.

- JSON serialization failure:
  NETWORK_ERROR.

- Fetch/network rejection:
  NETWORK_ERROR with raw cause retained.

- Non-2xx response:
  HTTP_ERROR with outer status only; response body ignored and not cancelled.

- 204 response:
  ok: true with runtime undefined cast to arbitrary T.

- Successful non-JSON response:
  INVALID_RESPONSE; body ignored and not cancelled.

- Successful JSON content type with empty body:
  INVALID_RESPONSE.

- Body stream failure:
  INVALID_RESPONSE with “Failed to parse response as JSON”.

- Malformed JSON:
  INVALID_RESPONSE with raw parse Error as cause.

- Valid JSON:
  ApiSuccess<T> after an unchecked compile-time assertion.

Positive error-handling properties:

- No catch-and-log-only block exists.
- The client returns failures rather than silently returning undefined.
- Non-2xx responses do not become success solely because Fetch resolved.
- Raw backend bodies and HTML are not exposed.
- Correction commit 8b8e1bb removed the initial 200-character backend-body preview.
- Caller abort listeners are removed for the pre-header operation and pre-aborted signals are handled.
- No automatic retry exists.
- Public routes do not currently display transport messages.
- Route placeholders do not pretend that backend requests succeeded.

Mandatory future mutation controls:

- Resolve redirect semantics before using postJSON for mutations.
- Define authentication, session, CSRF, and credential propagation deliberately.
- Never forward the full inbound Astro header set.
- Permit only specifically required outbound headers.
- Keep cookies, authorization, internal URLs, and diagnostic causes server-side.
- Preserve Django validation details through a reviewed structured envelope rather than raw backend output.
- Keep automatic write retries disabled unless method and idempotency semantics are explicitly defined.
- Apply runtime response validation at endpoint boundaries where malformed data could produce authoritative product output.
- Define request/response size limits.
- Test false-success paths, including redirects and bodyless results.
- Add correlation-safe logging without secrets, bodies, or stack traces in public output.
