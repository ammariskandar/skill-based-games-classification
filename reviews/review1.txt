Executive verdict

The project has a strong and unusually explicit product and architecture baseline for its early stage. The implemented foundation broadly follows the intended Astro MPA, hybrid-rendering, Tailwind CSS 4, Django, low-cost hosting, and read-only design-reference boundaries. The source is small, direct, readable, and free of speculative enterprise infrastructure. Challenge and Reward terminology is represented separately and consistently in current production-facing copy.

No Critical or High-severity defect was identified in the currently implemented application. The project is not release-ready, but that is predominantly normal incompleteness: Django Ninja, PostgreSQL, domain models, API routes, owner workflows, Steam integration, dynamic public pages, security hardening, and meaningful tests are explicitly scheduled for later Jira work.

Five material weaknesses should be addressed as foundation work continues:

1. The documented backend environment contract contains settings that are ineffective or unused.
2. The fallback Django secret permits unsafe production startup instead of failing safely.
3. CI does not yet enforce all locally documented gates and does not execute tests.
4. The npm lockfile records Tailwind packages under the wrong workspace ownership boundary.
5. Repository documentation contains stale statements that contradict the implemented Tailwind state.

Development should continue, with the environment-contract and dependency-lock issues corrected before dependent backend and frontend work expands. Security hardening must be completed before any public deployment.

Medium-priority findings

ID: REVIEW-1-01
Severity: Medium
Area: Security and privacy
Type: Security risk
Finding: Django falls back to a committed insecure secret when DJANGO_SECRET_KEY is absent, including when DEBUG is false.
Evidence: apps/backend/config/settings.py:30-34 assigns the default value “django-insecure-dev-key-do-not-use-in-production”; DEBUG defaults to False independently. docs/environment-variables.md:33 and 48 describe DJANGO_SECRET_KEY as required and state that production should fail safely when critical secrets are absent.
Why it matters: A production process with an incomplete environment can start using a known signing secret. This weakens session, message, password-reset, and other Django signing guarantees and contradicts the documented fail-safe policy.
Current impact: Local scaffolding can run without manual secret setup, but no deployed application was available to establish whether the fallback is currently exposed.
Future impact: A missed Render environment variable could silently produce an insecure public deployment.
Recommended action: During the planned backend-security work, separate explicitly local development defaults from production settings and require a non-placeholder secret whenever the application is not in an explicitly identified development mode. Add a deployment-oriented configuration check.
Suggested Jira scope: Include fail-closed secret validation and production configuration checks in the backend-security task; do not create a separate ticket if SBGC-41 has not begun.
Confidence: High

ID: REVIEW-1-02
Severity: Medium
Area: Architecture
Type: Confirmed defect
Finding: The advertised backend environment contract includes CORS_ALLOWED_ORIGINS and ADMIN_URL_PATH, but neither currently controls application behaviour.
Evidence: apps/backend/config/settings.py:42-46 reads CORS_ALLOWED_ORIGINS and ADMIN_URL_PATH. apps/backend/config/urls.py:21-23 hard-codes “admin/” instead of using ADMIN_URL_PATH. apps/backend/requirements.txt contains no CORS middleware package, and apps/backend/config/settings.py:51-68 registers no CORS application or middleware. apps/backend/.env.example:5 and 8 and docs/environment-variables.md:37 and 40 present these values as supported configuration.
Why it matters: Operators and future implementers may believe that changing these variables changes cross-origin or admin-routing behaviour when it does not. Configuration that is accepted but ignored is harder to diagnose than configuration that is explicitly deferred.
Current impact: ADMIN_URL_PATH changes have no effect. CORS_ALLOWED_ORIGINS is an inert custom Django setting. The current application has no public API, so the CORS omission does not yet break a user journey.
Future impact: Frontend-to-backend integration may fail unexpectedly, or an operator may incorrectly assume that the admin route has been changed or that CORS restrictions are active.
Recommended action: Make the environment documentation distinguish implemented values from reserved future values. When SBGC-40 and SBGC-41 are implemented, wire ADMIN_URL_PATH into URL configuration and either implement CORS deliberately or document why the server-to-server Astro architecture does not require browser CORS for a given endpoint.
Suggested Jira scope: Include ADMIN_URL_PATH wiring in SBGC-40 and effective CORS configuration in SBGC-41. Add acceptance checks proving that changed values affect runtime behaviour.
Confidence: High

Architecture assessment

The implemented architecture aligns with the accepted baseline.

apps/frontend/astro.config.mjs uses output: “server” with @astrojs/vercel, establishing SSR/on-demand rendering by default. index.astro, about.astro, and methodology.astro explicitly opt into prerendering. This matches the canonical Astro MPA with hybrid rendering.

There is no SPA router, client framework, or client-side business logic. The current source has no React, Vue, or Svelte production dependencies. The locked React/Vite prototype remains outside apps/frontend and is not part of the root npm workspace.

The intended frontend/backend boundary is well documented: Astro owns rendering and presentation; Django owns domain rules, persistence, API behaviour, Steam integration, and Django Admin. No implementation currently violates that boundary.

The Vercel/Render/Neon architecture is proportionate to the expected traffic and learning objectives. There is no Redis, Celery, Elasticsearch, Kubernetes, microservice decomposition, paid CDN, object-storage layer, or server-hosted LLM. This restraint should be preserved.

The all-dynamic-pages-through-Astro-and-Django request path introduces two potential cold-start points, but context.md explicitly accepts free-tier cold starts and low availability. It is not a defect at the expected scale.

The backend remains Django’s generated project shell rather than the planned games, classifications, and api application structure. This is normal incompleteness because SBGC-37 and subsequent backend tasks have not been implemented.

Product-alignment assessment

Current work supports the intended product rather than an unrelated technical showcase.

Production copy consistently identifies Micro, Mystiko, and Macro and explicitly mentions separate Challenge and Reward profiles. methodology.astro correctly states that the profiles describe composition rather than difficulty or quality.

No implemented feature conflates Challenge and Reward values. No obsolete Meso identifiers were found in current production application code. Historical Meso references are appropriately retained in the archived context and canonical history.

The owner-curated MVP, Steam/manual game distinction, approximately 200-game target, non-game exclusion policy, editorial/community separation, and Django Admin workflows are not implemented yet. These are planned foundations and features, not current defects.

No premature accounts, community voting, moderation, recommendation engine, WebLLM, analytics, or enterprise infrastructure were introduced.

The current informational pages are deliberately skeletal. Their limited content should not be mistaken for finished public product work; route and shell tasks remain in the documented Jira sequence.

Code and framework assessment

The current production source is small and easy to inherit. BaseLayout.astro provides a clear shared document shell. Page components are short, semantic, and contain no unnecessary abstraction or client-side JavaScript.

Tailwind CSS 4 is integrated through @tailwindcss/vite and @import “tailwindcss”, without a legacy @astrojs/tailwind adapter or unnecessary tailwind.config file. This matches the documented Tailwind 4 approach.

Astro configuration uses the intended server output and Vercel adapter. Fixed pages explicitly declare prerendering. TypeScript extends Astro’s strict configuration.

The Django code is mostly generated scaffolding with environment loading and SQLite fallback. It is readable and not over-engineered. Generated explanatory comments are verbose but harmless at this stage.

ADMIN_URL_PATH is currently dead configuration, and CORS_ALLOWED_ORIGINS has no enforcement mechanism, as recorded in REVIEW-1-02.

Frontend ESLint completed successfully. Frontend Prettier checking completed successfully. Ruff lint and Ruff formatting checks completed successfully.

Astro’s type check and production build were not run because they can create generated repository-local output, which would conflict with the strict read-only review boundary. Existing CI history was not accessible to independently confirm previous successful builds.
