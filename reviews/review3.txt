ID: REVIEW-3-01
Severity: Medium
Area: Django Ninja API contract
Type: Defect
Status relative to Review 2: New; SBGC-38 was implemented after Review 2
Finding: The standard 4xx/5xx response mapping uses the integer keys 4 and 5 rather than Django Ninja’s status-code sets, producing invalid OpenAPI response keys and no runtime schema for real 4xx/5xx endpoint results.
Evidence: apps/backend/api/errors.py:33 defines STANDARD_ERROR_RESPONSES = {4: ApiErrorResponse, 5: ApiErrorResponse}. apps/backend/api/system.py:15-18 expands these keys into the operation response declaration. The installed Ninja operation contains response-model keys 200, 4, and 5. A safe test-client probe showed OpenAPI response keys "200", "4", and "5". Django Ninja’s official API requires codes_4xx/codes_5xx or a frozenset of concrete status codes: [Django Ninja multiple response codes](https://django-ninja.dev/guides/response/).
Why it matters: OpenAPI clients and validators receive nonstandard response keys. A future endpoint returning a declared Status(404, payload) will not match key 4 and can raise Ninja ConfigError instead of serializing the error.
Current impact: The only real operation returns 200. Exception handlers return HttpResponse directly and therefore mask the declaration defect during existing tests.
Future impact: Every domain endpoint that spreads STANDARD_ERROR_RESPONSES can publish an invalid contract and fail when returning explicit error results.
Recommended action: Use Django Ninja’s documented codes_4xx and codes_5xx sets, or explicit status frozensets. Add tests that assert concrete 400/404/422/500 keys in OpenAPI and exercise an endpoint returning a non-2xx Status value through response-schema validation.
Suggested Jira scope: SBGC-38 corrective API-contract ticket, coordinated with SBGC-89/SBGC-100.
Dependencies or sequencing: Fix before defining the first domain endpoint schema.
Confidence: High

ID: REVIEW-3-02
Severity: Medium
Area: Steam trusted-origin boundary
Type: Security
Status relative to Review 2: New; SBGC-42 was implemented after Review 2
Finding: Steam API origins are public dataclass constructor fields rather than fixed trusted constants, allowing a directly constructed configuration to redirect API-key-bearing requests.
Evidence: games/services/steam/config.py:14-27 defines api_origin and store_origin as ordinary SteamClientConfig fields and __post_init__ does not validate them. client.py:201-218 concatenates config.api_origin and sends x-webapi-key. A fake-session probe using SteamClientConfig(api_key="SECRET", api_origin="https://attacker.example") showed the client targeting https://attacker.example/probe with the key header. config/steam.py’s factory omits origin overrides, but the dataclass is public and exported. config/tests/test_steam.py:607-622 proves only that Django setting overrides leave the factory defaults unchanged. context.md:2242 and docs/steam-integration.md:56-67 call the origins fixed constants.
Why it matters: The API-key secrecy guarantee depends on the destination origin being immutable. Constructor-level configurability makes the trust boundary depend on every future caller using the preferred factory correctly.
Current impact: No endpoint or concrete Steam adapter consumes the client, and no user-controlled input reaches the config. No active key exposure was demonstrated.
Future impact: A test override, management command, adapter, or refactor can pass a custom origin and silently forward a protected Steam key outside Valve.
Recommended action: Remove trusted origins from constructor input and represent them as module constants or ClassVar values. If testability requires substitution, inject a separate explicitly unsafe test transport rather than weakening production configuration. Add a direct-construction test proving origin replacement is impossible or rejected.
Suggested Jira scope: SBGC-42 corrective trusted-origin hardening; amend SBGC-53 acceptance criteria.
Dependencies or sequencing: Complete before any authenticated Steam endpoint, command, or scheduled import.

ID: REVIEW-3-04
Severity: Medium
Area: Steam retries and synchronous availability
Type: Performance
Status relative to Review 2: New; SBGC-42 was implemented after Review 2
Finding: The Steam retry policy does not implement its documented five-second delay bound and can block a synchronous worker for a Retry-After value up to six hours per retry.
Evidence: client.py:133-145 sets respect_retry_after_header=True but does not set backoff_max or retry_after_max. Installed urllib3 2.7.0 defaults to backoff_max=120 and retry_after_max=21600. A probe parsed Retry-After: 999999 as 21600 seconds. docs/steam-integration.md:93-100 states “no delay beyond 5 seconds.” Requests connect/read timeouts are not wall-clock deadlines and read timeout measures inactivity between bytes: [Requests timeout documentation](https://requests.readthedocs.io/en/latest/user/quickstart/?highlight=timeout). urllib3 documents the retry/backoff defaults: [urllib3 Retry reference](https://urllib3.readthedocs.io/en/stable/reference/urllib3.util.html).
Why it matters: A trusted upstream 429/503 response can hold a synchronous Django worker far beyond provider and request budgets. With max_retries=3, the policy permits the initial request plus three retries, not three total attempts.
Current impact: No endpoint invokes the client. Tests inspect adapter properties but do not execute retry sleep behavior.
Future impact: A Steam degradation or rate limit can exhaust workers, extend cold-start/serverless invocations, and amplify upstream load.
Recommended action: Define an explicit wall-clock budget and retry contract. Set an intentional short backoff_max and retry_after_max, or disable automatic Retry-After sleeping and surface retry metadata to the caller. Add behavior tests with sleep replaced by a spy; assert attempts, delay caps, 429 handling, and exhausted status behavior.
Suggested Jira scope: SBGC-42 retry correction, incorporated into SBGC-53 before endpoint work.
Dependencies or sequencing: Fix before any synchronous request path consumes Steam.
Confidence: High
